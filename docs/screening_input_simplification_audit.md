# 審査入力項目の簡便化調査

作成日: 2026-07-31

## 結論

審査システムを使い続けるには、入力項目を削るより先に「通常入力で見せる項目」を減らすべき。

現状は、スコア本体、補助診断、稟議コメント、将来分析、デモ用入力が同じ重さで並んでいる。モデル側の互換性を壊さずに簡便化するなら、API payload は維持し、UI を以下の3層に分ける。

- 最小入力: 毎回入れる項目。
- 条件入力: 新規先、競合あり、高額案件、違和感ありの時だけ出す項目。
- 詳細入力: OCR、稟議コメント、将来分析用。折りたたみでよい項目。

## 現状の主な入力源

- 型定義: `frontend/src/types/index.ts`
- 基本情報: `frontend/src/components/form/FormGeneral.tsx`
- 財務情報: `frontend/src/components/form/FormFinancial.tsx`
- 物件・定性: `frontend/src/components/form/FormQualitative.tsx`
- APIスキーマ: `api/schemas.py`
- スコア本体: `scoring_core.py::run_quick_scoring`

## 通常入力に残す項目

最初の簡便版では、以下を第1画面に残す。

- 企業番号 または 企業名
- 業種大分類
- 業種中分類
- 格付
- 顧客区分
- メイン先区分
- 売上高
- 営業利益
- 経常利益
- 当期純利益
- 純資産
- 総資産
- 銀行与信残高
- リース与信残高
- 契約件数
- 対象物件
- 取得価額
- リース期間
- 直感スコア
- 現場メモ

理由: スコア、信用警戒、比較コメント、紫苑レビューに直接効く。ここだけで初回の審査仮説は作れる。

## 条件付きで出す項目

以下は常時表示しなくてよい。

- 競合状況: 新規先、または現場メモに競合・相見積もりがある場合だけ表示。
- 競合社数: 競合ありの場合だけ表示。
- 競合提示金利: 競合ありの場合だけ表示。
- 発生経緯: 新規先または競合ありの場合だけ表示。
- 商談ソース: 既定値を銀行紹介にし、変更時だけ表示。
- 契約種類: 既定値を一般にし、自動車・割賦の時だけ変更。
- 営業部: ログインユーザーや過去案件から補完できるなら隠す。
- 物件確認資料: 高額案件、物件説明不足、稟議コメント生成時だけ表示。

## 詳細入力へ退避できる項目

以下はスコアや補助診断で参照されるが、毎回手入力するには重い。OCRまたは詳細折りたたみに逃がす。

- 売上総利益
- 減価償却費（資産）
- 減価償却費（経費）
- 賃借料（資産）
- 支払リース料
- 機械装置・運搬具
- その他固定資産
- 型式・メーカー・仕様
- 設置場所・使用場所
- 導入目的・用途
- 定性評価6項目

注意: 売上総利益、償却、機械装置、その他固定資産、支払リース料はRFモデルや警戒診断に入るため、完全削除ではなく「未入力なら0/default、OCRがあれば反映」が安全。

## スコアリング影響確認

詳細財務を0扱いにすると、スコアは大きく変わる。削除不可。

コード上の参照:

- `gross_profit`, `machines`, `other_assets`, `depreciation`, `dep_expense`, `rent_expense` は `scoring_core.py::data_scoring` と `scoring.predict_one()` に渡される。
- `rent_expense` はリース費用比率と `lease_ratio_adj` に使われる。
- `depreciation`, `machines` は `quantum_analysis_module.compute_simple_q_risk()` の設備矛盾検知に使われる。
- `gross_profit`, `depreciation`, `machines`, `other_assets`, `rent_expense` は高リスク財務パターン警告にも使われる。

簡易実測:

- 建設業サンプル: 詳細財務あり `score=64.1` / 詳細財務0 `score=82.5`。判定が要審議から承認圏内へ反転。
- 製造業サンプル: 詳細財務あり `score=55.8` / 詳細財務0 `score=76.4`。判定が要審議から承認圏内へ反転。
- 新規飲食サンプル: 詳細財務あり `score=93.5` / 詳細財務0 `score=0.0`。モデル経路上、詳細財務欠落で極端に変動。

結論: 詳細財務は通常画面から隠してよいが、スコアリング上は「入力不要」ではない。クイック審査では概算値/OCR/前回値/業種中央値などで補完し、本審査では手入力またはOCR確認を必須にする。

## 削除または非表示候補

以下は現状の主スコアAPIでは重要度が低い、または将来分析用に近い。

- 3期分トレンド格付: `ScoringRequest` に明示定義がなく、主スコアでは直接使われていない。将来分析へ移す。
- 検収年: 主スコアでは直接参照されていない。結果登録または稟議補助へ移す。
- 詳細キーワード: 業種推定用としては有用だが、通常は物件名・企業名から推定し、必要時だけ表示。
- `asset_score`: 未入力なら50扱い。人間が毎回点数化するより、物件名・期間・用途から警告生成する方が自然。

## 推奨UI

### クイック審査

第1画面は20項目前後に抑える。足りない項目は「未入力だが計算可能」として進ませ、結果画面で不足入力を表示する。

### 詳細審査

財務明細、物件明細、定性6項目、競合条件を展開できるようにする。OCRを使った場合は詳細欄へ自動反映する。

### 紫苑補完

現場メモから以下を推定して候補表示する。

- 業種候補
- 競合あり/なし
- 導入目的
- 物件用途
- 確認すべき不足項目

ただし自動確定はしない。Userが押して反映する。

## 実装優先度

1. `FormGeneral` の3期分トレンド格付を折りたたみへ移す。
2. `FormFinancial` の詳細財務を「OCR/詳細」折りたたみへ移し、通常は主要7項目だけにする。
3. `FormQualitative` の物件明確化と定性6項目を折りたたみへ移す。
4. 競合関連は `competitor === "競合あり"` または `customer_type === "新規先"` の時だけ表示する。
5. `/api/score/full` の結果に `missing_but_optional_inputs` を返し、未入力でもどこが弱いかを画面に出す。

## 内政モード判断

これは採用候補。成功指標は以下。

- クイック審査の初回実行までの入力時間
- 1案件あたり手入力項目数
- 審査実行回数
- 不足入力警告を見た後の追加入力率
- 紫苑レビューへの `useful` 反応率

リスクは、入力を隠しすぎてスコア根拠が薄く見えること。対策として「詳細入力を削除しない」「未入力項目を結果画面で明示する」こと。
