# Shion Information Health

作成日: 2026-07-28

## Purpose

紫苑の次の運用方針は、情報源を増やすことではなく、情報の健康を保つことに置く。

情報健康とは、紫苑が多くの記憶・改善ログ・判断資産・内省・監視レポートを持っていても、毎回それらを同じ重さで読まず、必要なものだけを短く使い、行動へ移す前に人間の判断を通す状態を指す。

## Core Rule

紫苑に見せるものは増やしてよいが、紫苑が従うものは増やさない。

## Three Lanes

| lane | purpose | examples | action rule |
|---|---|---|---|
| 見るだけ | 状態把握・異常検知 | 日次改善レポート、Obsidian監視、成長スコア、眠ってる判断資産 | 回答の背景に使うだけ。判断・実装・昇格へ直結しない |
| 相談に使う | Userと次の一手を選ぶ | 朝の改善カルテ、今日見る1件、要レビュー、helped/rejected | 最大数を絞って短く出す。Userが選ぶ |
| 行動に使う | 実装・昇格・判断変更 | User明示承認、User修正文、結果登録で検証された判断資産 | 人間承認後だけ実行・昇格・反映する |

## Display Budgets

通常のチャットやホームで紫苑に渡す情報量は、以下を上限にする。

- 朝の改善カルテ: 最大5行
- 改善候補: 最大3件
- 判断資産候補: 最大3件
- 警告: 最大2件
- 価値記憶・良心チェック: 高影響・迷い・説明責任がある時だけ
- スコアリング・承認/否決判断: 日次改善、bandit、内省からは変更しない

## Health Signals

次の兆候が出たら、新機能追加ではなく整理を優先する。

- 同じ改善候補が毎日出る
- `needs_review` が減らず、Userが見なくなる
- 判断資産が増えるが `helped` が増えない
- `sleeping` active rule が多く、使われないまま残る
- 紫苑がレポートや記憶を根拠に、実案件の確認より先に断定する
- 内省・改善・記憶・判断資産の境界が曖昧になる

## Operating Mode

当面は「整える運用」を優先する。

1. 毎朝は全部読まず、朝の改善カルテだけ見る。
2. 気になった時だけ改善ログや判断資産レビューへ降りる。
3. 判断資産は増やすより、使ったか・効いたか・外したかを見る。
4. 使われないものは削除ではなく、sleeping / stale / review として棚卸しする。
5. 新しい自動化は、既存ループのノイズを減らす場合だけ検討する。

## Guardrail

日次改善レポート、朝の改善カルテ、bandit-style 学習、Private Reflection は、紫苑の状態認識と相談材料である。これらを、審査スコア、承認/否決、自動昇格、自動デプロイへ直接つなげない。

## Evaluation GUI

`/shion-eval-health` は ADK eval の考え方を借りた、紫苑の情報健康チェック画面である。

- 評価対象は最終回答だけでなく、`memory_debug`、`knowledge_refs`、日次カルテ注入、判断学習使用、参照量、停止線で見る。
- 評価ケースは小さな golden set として保つ。ケースを増やしすぎず、紫苑が壊れやすい問いだけ残す。
- 採点は実装・審査・承認・判断資産昇格を自動実行しない。Userが見るための診断である。
- 失敗時の次の行動は、まずプロンプトや情報量の整理を検討する。新しい自動化追加は最後にする。
