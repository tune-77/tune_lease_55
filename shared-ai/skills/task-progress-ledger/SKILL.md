# Task Progress Ledger

理由: 複数タスクをsubagentに委譲する実装では、どのタスクが完了しどの指摘が未解決かがセッション圧縮や中断で失われやすい。またレビュー指摘への対応をラウンド数の上限なしに続けると収束しない。
適用条件: `planning-and-task-breakdown` で作成した計画のタスクを、Agent toolで複数の実装者subagent・レビュアsubagentに分けて進める時。
削除条件: ハーネス側にタスク進捗の永続追跡とレビュー往復回数の上限が標準機能として備わった時。

## 適用範囲

- **対象**: 計画済み・独立性の高い複数タスクを、実装者subagentとレビュアsubagentに分けて進める作業。
- **対象外**: 単一タスク・単一ファイルの実装（`incremental-implementation` で十分）。単一diffのcommit・push・PR作成・Codexレビュー対応は `git-ship` の範疇。**このスキル自体はPR作成やmergeを行わない** — 全タスク完了後は `git-ship` に引き継ぐ。

## 1. 台帳ファイル

- 場所: `.claude/state/task-ledger/<plan-slug>.md`（`.claude/state/` は `.gitignore` 済みのローカル専用領域なので、コミット対象にならず気軽に読み書きできる）
- 内容: タスクごとに1セクション。ステータス（`in_progress` / `done` / `parked`）、担当subagentのモデル、コミット範囲、指摘と対応状況、Rulingを記録する。

```markdown
## Task 3: 支払いスケジュール計算のバグ修正
- status: done (1 parked)
- implementer: claude-sonnet-5 (round 1) → claude-opus-5 (round 2, escalated)
- commits: a1b2c3d..e4f5g6h
- findings:
  1. [ADDRESSED] 端数処理がfloatのまま → Decimal化して修正
  2. [PARKED] 命名の不統一（レビュアの好み、依頼範囲外）
     Ruling: 対応しない — 既存命名規約に反しない軽微な指摘 — 誤っていた場合のコスト: 低（次回リネームで吸収可能）
```

## 2. タスク実行ループ

1タスクにつき:

1. Agent toolで実装者subagentを派遣する。渡す情報:
   - タスクの要約と受け入れ条件（`planning-and-task-breakdown` の計画から抜粋）
   - 対象範囲。**このリポジトリの絶対厳守事項を明記する**: 指示された箇所だけ変更する／`eslint --fix` 禁止／`data/` と `.streamlit/secrets.toml` はコミット禁止／`scoring_core.APPROVAL_LINE` 等のハードコード複製禁止
   - 先行タスクからの依存情報
2. 実装者の完了報告（テスト結果を含む）を受けたら、Agent toolで**別の**レビュアsubagentを派遣する。渡す情報:
   - タスク要約と実装差分（`git diff <base>..<head>`）
   - CLAUDE.mdの絶対厳守事項
   - `code-review-and-quality` の五軸基準（正確性・可読性・アーキテクチャ・セキュリティ・性能）
3. レビュアが指摘を返したら台帳に記録し、次節の修正ループへ進む。

## 3. 5ラウンド修正ループ

- **ラウンド1〜3**: 同じ実装者subagentに、未解決の指摘を逐語的に渡して修正させ、再度レビュアに確認させる。
- **ラウンド4〜5**: より高性能なモデルで新規の実装者subagentを派遣する。「先の実装者がN回試行済みで引き継ぐ」という前提を渡す。
- **5ラウンドを超えても指摘が解決しない場合**、それ以上は派遣しない。各指摘を次のいずれかで決着させ、台帳にRulingとして記録する:
  - レビュアが誤っている、または議論の余地がある → 対応しないRuling
  - 実害はあるが後続タスクに影響しない軽微な指摘 → 対応を延期するRuling
  - 実害があり構造的な問題 → 修正が必要と判断し、計画自体の見直しをユーザーに相談する
- subagent派遣時はモデルを常に明示指定する（省略すると高額モデルを暗黙に継承する）。

## 4. 全タスク完了後

- 台帳の全Rulingを一覧化してユーザーに報告する（何に対応し、何をなぜ対応しなかったか）。
- ここから先のcommit整理・PR作成・Codexレビュー対応は `git-ship` に引き継ぐ。PRタイトルへのREV番号付与など `git-ship` 側のルールに従う。
- 台帳ファイルは次回参照のため残してよい。ユーザーが不要と判断すれば削除する。

## 禁止事項

- 実装者の報告が不完全（テスト結果の提示がない）まま次のタスクへ進まない。
- レビュー指摘を台帳に記録せず黙って握りつぶさない。
- 5ラウンドを超えてさらに派遣を続けない。
- このスキル自身がPR作成・merge・ブランチ削除を行わない（`git-ship` の役割）。
