# Jev と Cloudflare Clef / Clef-flash の比較（2026-10-04）

Clef（@cf/cloudflare/clef）と Clef-flash（@cf/cloudflare/clef-flash）は TypeSafe System One と同じ
state / questions / answers の形で呼べる（`clef_client.py`。Cloudflare の封筒 `result` を剥がすだけ）。
`compare.py` はこれまでの Jev 評価セットの「送った伏せ字済み本文とラベル」を読み直し、
同じ組み立て関数・質問文・バッチ幅で3モデルへ送る。判定は REV-424 判定ログへ
`guard=<元のguard>:<model>`・`mode=offline_model_compare` で記録した（365件×3モデル、ラベル付き）。

- 分類（1件の文の性質）: Clef は Jev と同等（差は誤差の範囲）。生の確率の当たり（Brier）は Clef が良く、
  チャットでは Jev の生確率の偏りが大きい（0.285）。Platt 補正後も Clef がやや良い。
- 2つの文の比較（同一性・上書き）: Jev が有意に上。Clef-flash はほぼ当て推量（0.52）。
- 16件の評価は区間が広すぎて結論を出せない。
- 失敗 0 件（1,095 判定）。

## 運用面

- 送り先: Jev は TypeSafe、Clef は Cloudflare。shion.tune77.com の通信はすでに Cloudflare を通っているので、
  新しい送り先は増えない。ただし Workers AI の入力データの扱い（学習利用・保持期間）は規約を確認していない。
- 障害時: どちらも外部 API。既存の各ガードは失敗したら判定なしで今の動作を続ける作りなので、
  Clef にしても同じ（Clef 不通なら Jev、のフォールバックは今回は入れていない）。
- レート制限: Workers AI のモデル別の上限は未確認。今の量（RAG 並べ替えで約73リクエスト/日）なら問題になりにくい。
- コード変更量: 送信先と応答の封筒を剥がすだけ（`clef_client.py`）。ただし既存の Platt 係数
  （例: `typesafe_news_guard.REPAYMENT_PLATT_A/B`）は Jev の確率に合わせたもので、切り替えるなら付け直しが必要。
- ローカル実行（Ollama の clef-flash / clef）: 試していない。重みが clef-flash 約11GB・clef 約18GB で、
  この Mac の空きディスクが約19GB（使用率96%）しかなく、GPU なしの Core i5-8500 では1判定に数十秒かかる見込み。

## 結論

- 切り替えない。判別力で Clef が Jev を明確に上回る用途は無く、2文の比較では Jev が有意に上。
- 分類系（ニュース・チャット）は同等で、Clef の利点は生確率の当たりの良さだけ。Jev 側の Platt 補正で埋められる差で、
  費用は約4倍になる。
- Clef-flash は速い（往復の中央値で Jev の約半分）が、どの評価でも Jev より下。
