# TypeSafe/Jev 物件スコア推定 — Phase 0（実測のみ）

## 結論：**Phase 1 に進まない。教師データが存在しないため検証不能。**

当初の仮説は「`asset_score` 未入力時のデフォルト 50 は判断ではなくプレースホルダ
なので、品名から Jev に推定させれば埋まる」だった。DB を実測した結果、この仮説は
**検証できない**ことが分かった。Jev の性能が悪いのではなく、比較対象となる
「人間の判断」がデータ中にほぼ存在しない。

詳細は `measure.py` 冒頭のコメントブロックに証拠付きで残してある。要点：

1. **コーパスの大半は試験バッチ**。2026-06-29 の1日だけで 202 行あり、
   同一品名「CNC複合加工機」に対して 80/75/70/68/66/65/64/62/60/55/54/50/45/40/35 が
   それぞれ 10 行ずつ並ぶ。これは感度試験のスイープであって審査判断ではない。
   中央値を取っても「スイープした範囲の真ん中」が出るだけで意味がない。
2. **直近2か月（2026-07-19 以降）の 241 件に、人手入力された物件スコアは1件もない**。
   228 件が `None`、13 件が 50.0 ちょうど。本番で物件スコア欄は事実上使われていない。
3. 残る非 50 の値も、CNC マシニングセンタと一般乗用車が同じ 78.0 になるなど、
   物件の性質と対応していない。定数 78 の MAE が 5.00 しかないことがその裏返しで、
   これは「78 が定型値である」ことの証拠であって、Jev が超えるべき基準ではない。

**Phase 0 は失敗ではない。** 本番経路ゼロで測ったからこそ、架空の正解データの上に
機能を積む前に止められた。`typesafe_asset_guard.py` と本モジュールは、教師データが
実際に蓄積された時点で再利用できるよう保存する。

### 再開条件

本番で物件スコアが実際に入力されるようになること。現状その前提が崩れている理由は
下記の欠陥にあるため、まずそちらの解消が先になる。

## 実測中に見つかった本番の欠陥（本実験より重要）

### 1. `used_default_asset_score` が API 経由では決して立たない

- `api/schemas.py:45` — `asset_score: Optional[float] = Field(default=50.0, ...)`
- `api/main.py:1475` / `:1555` — `inputs = req.model_dump()` をそのまま渡す
- `scoring_core.py:755` — `_raw_asset_score is None or str(...).strip() == ""` でのみ判定

スキーマが未入力を 50.0 で埋めてから渡すため、`scoring_core` から見ると
「担当者が 50 と入力した」と区別がつかない。実測で確認済み：

```
model_dump()["asset_score"] = 50.0
used_default_asset_score     = False   ← 未入力なのに立たない
```

このフラグの利用箇所（すべて機能していない）：

| 参照元 | 用途 |
|---|---|
| `scoring_core.py:991` | 警告文「物件スコア未入力のためデフォルト値(50)を使用」 |
| `lease_intelligence_mind.py:1633` | 認知的不協和シグナル |
| `api/prediction_snapshot.py:72` | confidence の根拠記録 |
| `.claude/agents/scoring-auditor.md` | 「フラグが立った案件をリストアップ」する監査エージェント |

### 2. デフォルト 50 は人手入力の中心から離れている可能性

非 50 の値だけを見ると最良定数は 78（MAE 5.00）。もし人間が通常 78 前後を書くなら、
未入力案件に 50 を当てる現行挙動は物件スコアを一律に約 28 点低く見積もっている。
ただし上記のとおり 78 自体が定型値の疑いが濃いため、**この数値で本番を変更しては
いけない**。実入力が溜まってから再測定する。

## 設計上の約束（Phase 1 以降に再開する場合）

- 計算はコードに残す。Jev が答えるのは `category_config.CATEGORY_SCORE_ITEMS` の
  次元ごとの1問だけで、重みと加重平均は `asset_scorer.calc_asset_score` のまま。
  重みを変えても再推論が要らず、監査可能性も落ちない。
- 1物件の全次元を**1リクエストにまとめる**（各判断は相互に独立）。
- 外に出るのは担当者が書いた品名・補足・カテゴリ・リース期間のみ。企業名・財務数値・
  案件IDはローカルに残す（`.claude/rules/security.md`）。
- 失敗は fail-open。空の dict が返り、`calc_asset_score` が全項目 50 で埋める＝現行と同一挙動。

**本番経路はゼロ。** `typesafe_asset_guard.py` はどのモジュールからも import されて
いない。`scoring_core.py` / `asset_scorer.py` / FastAPI ルータは未変更。

## 教師データの切り出し方（`admit_row`）

DB には2つの入力フォームの履歴が混在する。

| 母集団 | キー | 期間 |
|---|---|---|
| A | `lease_asset_name` + `lease_asset_score` | 旧フォーム |
| B | `asset_name` + `asset_detail` + `asset_score` | 2026-06 以降 |

2026-06 以降は同一案件が両形式で1〜2秒差で二重記録されるため、A は
`[ERA_START_MONTH, B_ERA_START_MONTH)` のみ、B は全期間を採用する。
また 2026-05 より前は 100.0（＝「処分リスクゼロ」、中古重機にもあり得ない値）が
全体の 43〜44% を占めるため除外する。時刻で切っており、値での除外はしていない。

単位は**行数ではなく異なる設問数**。「CNC複合加工機 / 新品」の 56 行は
1問を56回答えたものに過ぎず、信頼区間は設問数でしか縮まらない。

`fixtures/` と `results/` は案件由来データを含むため `.gitignore` 済み。

## 使い方

```bash
python3 experiments/typesafe_asset/measure.py --seed     # DB から教師データ生成
python3 experiments/typesafe_asset/measure.py            # 件数・分布の確認（通信なし）
python3 experiments/typesafe_asset/measure.py --inspect  # 送信ペイロードを全文表示
TYPESAFE_ASSET_ENABLED=1 TYPESAFE_API_KEY=... \
  python3 experiments/typesafe_asset/measure.py --send   # 送信
python3 experiments/typesafe_asset/measure.py --sweep results/judged_*.json
```

`--inspect` で全文を目視してから `--send` する2段ゲート。`--send` は
`TYPESAFE_ASSET_ENABLED` と API キーの両方が揃っていなければ何もせず終了する。
**現時点で `--send` は一度も実行していない。**

再開する場合、`admit_row()` を書き換えて `--seed` をやり直せばコーパスを切り直せる
（`--seed` は追記のみなので、切り直す際はフィクスチャを空にしてから実行する）。

## 判定基準（再開時）

比較対象は次元ごとの値ではなく、`calc_asset_score` を通した合成スコア（0-100）。
人手の `asset_score` が合成値なので次元ごとの正解は存在せず、測っているのは
「Jev の次元判定 ＋ 既存の重み」がセットで人間に一致するか＝本番で使う経路そのもの。

**基準は「50 固定に勝つこと」ではなく「最良定数に勝つこと」。** 最良定数とは MAE を
最小化する単一の固定値で、`measure.py` が毎回計算して表示する。50 固定に勝つのは
自動的で、何も証明しない。

設問数が 20 を下回るうちは差が偶然の範囲に収まるため、`measure.py` が警告を出す。

## 未決事項（再開時に持ち越し）

- `LEVEL_LADDER` は「処分価値」軸の4段階。「標準」が 66.7 点に対応する。審査実務が
  標準的な物件を 50 点前後と見るなら5段階に組み直す必要がある。
- 医療機器の `regulatory_risk`（薬事規制リスク）は処分価値軸に素直に乗らない。
  `DIMENSION_LEVELS` に専用の段階を足すことになる可能性が高い。
- `MIN_CONFIDENCE = 0.30` は暫定値。実測で決める。
- カテゴリ推定（品名 → `IT機器`/`産業機械`/`車両`/`医療機器`）は現在キーワード表で
  行っているが、「アルファード」「三菱 スーパーグレード」のような車種名は原理的に
  拾えない。ここは Jev の Choice プリミティブの適所。ただし Jev の推定カテゴリで
  Jev を評価すると循環するため、Phase 0 では採用していない。
